# Plone Aurora development

Use this skill when working on a Plone Aurora repository, application, frontend
add-on, or package. Aurora is the React-based frontend for Plone and
`plone.restapi`, and is the successor to Volto.

## Identify the project

First inspect the repository before choosing commands or architecture:

- Read the root `AGENTS.md`, then any package-level `AGENTS.md` files relevant to
  the change.
- Check `package.json`, `pnpm-workspace.yaml`, lockfiles, and package scripts.
- Look for `apps/aurora`, `packages/*`, `backend/`, `frontend/`, and `devops/`.
- Determine the Node.js and pnpm versions from repository metadata and CI. Do
  not rely on possibly stale online version-policy pages.

Classify the project as one of these:

| Project | Indicators | Typical purpose |
| --- | --- | --- |
| Aurora core | `apps/aurora` and many `packages/*` workspaces | Core app and libraries |
| Full project | `backend/`, `frontend/`, and `devops/` | A deployable site with a customizable Python backend |
| Frontend add-on | An add-on package, usually generated by Cookieplone | Reusable frontend-only functionality |

For Aurora core, use **pnpm**. Do not substitute npm or Yarn unless the
repository explicitly instructs you to do so. For generated projects, follow
their local Makefile and package-manager instructions.

## Architecture

Aurora is assembled from focused packages:

- `apps/aurora`: application shell and routes.
- `@plone/publicui`, `@plone/layout`, and `@plone/blocks`: visitor-facing UI
  and rendering.
- `@plone/cmsui`, `@plone/contents`, `@plone/plate`, `@plone/blocks`, and
  `@plone/layout`: editing experience.
- `@plone/client`, `@plone/registry`, and `@plone/react-router`: API access,
  extensibility, routing, loaders, and actions.
- `@plone/types` and `@plone/helpers`: shared contracts and utilities.
- `@plone/components`, `@plone/agave`, and theming packages: UI primitives and
  themes.

Prefer the documented extension points over changing app internals. Aurora's
main design differences from Volto are:

- React Router loaders and actions replace Redux-driven data flow.
- Server-side rendering keeps the Plone API behind the application server.
- TypeScript is the default for new core and add-on code.
- Plain CSS is the default styling approach; Tailwind is optional.
- Shared client state should be introduced only when loaders/actions do not fit;
  follow the repository's existing state-management patterns.

`@plone/plate` provides the unified Somersault editor. It represents page text
and traditional Plone blocks in one Plate tree, with legacy content normalized
on the server. The unified editor is still under active development, so avoid
depending on undocumented internal data shapes such as `__somersault__` unless
the task specifically concerns that implementation.

Do not make significant changes to `packages/volto` or `packages/volto-slate`.
They are legacy reference packages unless the task explicitly targets them.

## Add-on development

Use the configuration and add-on registries rather than forking Aurora. An
add-on normally exposes a root `index.ts` through its `package.json` `main`
entry:

```ts
import type { ConfigType } from '@plone/registry';

export default function loadConfig(config: ConfigType) {
  config.blocks.blocksConfig.myBlock = myBlockConfig;
  return config;
}
```

Add-ons can register or customize:

- Blocks, content types, schemas, and migrations.
- Routes, components, utilities, and slots.
- Toolbar actions, icons, styles, and themes.
- Client configuration and optional server-only configuration in `config/server.ts`.
- Vite configuration through the documented extension mechanism.

Register the add-on through the project's documented `addons` configuration or
`package.json`. Configuration loaders run in registration order; preserve
existing entries when extending arrays or maps unless replacement is
intentional. Do not edit generated `registry.loader.js` or
`registry.loader.server.js` files.

Only registered add-ons should be shadowed. Prefer a public registry, slot, or
component adaptation before shadowing a module.

An add-on package contains frontend code only. If the feature needs Python
content types, behaviors, workflows, or REST API services, use a full project
with a backend instead.

## Core setup and commands

For Aurora core, the documented baseline is:

```sh
make install
make backend-docker-start
pnpm start
```

The backend normally serves on `http://localhost:8080` and the frontend on
`http://localhost:3000`. The backend Docker volume is intended for development,
not production.

Run commands from the root or scope them with pnpm filters. Prefer the scoped
form while iterating:

```sh
pnpm --filter @plone/<package> test --run
pnpm --filter @plone/<package> build
pnpm --filter @plone/<package> check:ts
```

Common repository-wide checks, when defined by the repository, include:

```sh
pnpm lint
pnpm test:ci
pnpm check:ts
pnpm acceptance-test
pnpm prettier:fix
pnpm stylelint:fix
```

For a full Cookieplone project, use its Makefile targets, typically `make
install`, `make backend-start`, and `make frontend-start`. For a frontend-only
add-on, the generated workflow typically uses `make install`,
`make backend-docker-start`, and `make start`.

Do not invent scripts. Inspect the applicable `package.json` or Makefile first.

## Validation workflow

Use the smallest relevant checks first, then expand for cross-package changes:

1. Run the target package's unit tests and type check.
2. Run its build when exports, dependencies, or bundling changed.
3. Run lint and formatting checks for changed files.
4. Run Playwright acceptance tests when routing, API integration, editor
   behavior, or user-facing flows changed.
5. Run documentation checks when documentation or public APIs changed.

Aurora core uses Vitest for unit tests and Playwright for acceptance tests. Use
the browser skill for visual or interactive verification of a running frontend;
wait for the server to respond before opening the browser.

When changing a shared package, inspect its consumers and test the affected app
as well as the package itself. Keep changes package-local unless the change is
clearly cross-cutting.

## Public API and contribution rules

Treat these as public contracts unless repository guidance says otherwise:

- Public UI component props and DOM structure.
- Default blocks and their schemas/components.
- Helpers and documented registry APIs.
- Stable classes and styling hooks used by integrators.

DOM removals, property removals, and even added structural DOM elements can be
breaking for downstream themes. Document breaking changes in the upgrade guide
and include the required changelog/news entry with the repository's expected
attribution format.

Before proposing a contribution:

- Check for an existing issue or pull request.
- Follow the repository's contributor agreement and branch policy.
- Open ordinary feature and bug-fix changes against the branch specified by the
  current repository guidance, usually `main`.
- Include tests and documentation for user-visible or public API changes.

## Common pitfalls

- Do not use npm or Yarn for Aurora core.
- Do not edit generated registry loader files.
- Do not assume a frontend-only add-on can customize the backend.
- Do not rely on legacy Volto architecture when an Aurora registry, loader,
  route, slot, or adapter exists.
- Do not trust stale documentation over local package scripts, CI, or
  `AGENTS.md` instructions.
- Do not commit credentials, environment-specific values, or generated build
  artifacts.
